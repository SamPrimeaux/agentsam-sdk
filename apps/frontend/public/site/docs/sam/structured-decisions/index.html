Agent architecture

Structured decisions with coding agents

Coding agents are good at language, planning, tool use, and code generation. They should not have to improvise every small decision in prose. AgentSam pairs an LLM with a faster, typed decision layer for routing, scoring, confidence checks, utility selection, and policy gates.

Core idea: use the LLM for open-ended reasoning; use typed decision primitives when the answer must fit a known shape and directly control software behavior.

This is not another chat model

The structured layer is not responsible for holding a conversation, writing a React component, explaining a bug, or generating a migration. Those remain LLM jobs.

Its job is narrower: receive a known state, evaluate a constrained question, and return a typed result that software can consume without parsing prose.

ProblemUse
“Explain why this terminal session failed.”LLM
“Which execution lane should handle this command?”choice
“How risky is this deployment?”score
“Is confidence high enough to act without asking?”gate
“Rewrite this package boundary cleanly.”LLM + tools

Where it fits in AgentSam

AgentSam already has many places where the possible outputs are constrained. Those are ideal for typed decisions instead of open-ended generation.

/

Skills

›_

Terminal

Choose local, remote, or sandbox execution from observed runtime state.

◇

Retrieval

Select memory, AST-RAG, docs, repository index, or no retrieval.

M

Models

Route between fast, reasoning, local, or provider-specific models.

↑

Deploy

Primitive 1: State

A decision should be grounded in explicit machine-readable state, not hidden prompt assumptions. State can combine repo facts, runtime health, user intent, tool availability, cost budget, security constraints, and previous action results.

decision-state.ts
const state = {
  intent: "inspect_repository",
  repo: { dirty: true, tests: "unknown", packageCount: 31 },
  terminal: { local: "healthy", remote: "healthy", sandbox: "available" },
  policy: { allowProductionWrite: false }
};

Primitive 2: Choice

A choice selects one item from a finite candidate set. Ideal when AgentSam already knows the legal options.

conceptual contract
{
  question: "Which execution lane should run this task?",
  options: ["local", "remote", "sandbox"],
  result: "local",
  confidence: 0.94
}

Good AgentSam uses: tool selection, skill selection, retrieval lane, model class, workflow branch, terminal target, next GOAP action.

Primitive 3: Score

A score maps state onto a bounded rubric. The number is useful because AgentSam can compare options or apply thresholds without asking an LLM to emit JSON-shaped prose.

utility.ts
type ActionScore = {
  action: string;
  utility: number;      // 0..1
  risk: number;         // 0..1
  cost: number;         // 0..1
  reversibility: number; // 0..1
};

Primitive 4: Gate

A gate turns a structured assessment into permission to continue. Gates protect actions with consequences: production writes, secret rotation, package release, destructive database changes, or expensive long-running jobs.

candidate action
     │
     ▼
risk score ───────┐
confidence ───────┤
tests/status ─────┤──► gate policy ──► allow
approval state ───┤                 └─► ask user
reversibility ────┘                 └─► deny

Primitive 5: Confidence

Confidence is not a substitute for correctness. It is a routing signal. The important behavior is what AgentSam does when confidence is low.

ConfidenceAgent behavior
HighProceed when policy allows; record the decision and evidence.
MediumGather one more piece of evidence, run a cheap check, or compare alternatives.
LowAsk the user, defer, or route to a stronger reasoning model.

Pattern: Intent routing

01

Route before generating

Classify the task into a known execution family, then hand the task to the correct subsystem.

request → {code | research | terminal | database | deploy | design | document} → route

This keeps the expensive language model focused on the actual job instead of repeatedly rediscovering which AgentSam subsystem should own it.

Pattern: Utility scoring

Utility scoring lets multiple possible actions compete using explicit factors. This matches AgentSam’s machine-agent layer.

utility formula
utility =
  (goalProgress * 0.40) +
  (confidence   * 0.20) +
  (reversibility * 0.15) +
  (speed        * 0.15) -
  (risk         * 0.25) -
  (cost         * 0.10);

The exact weights should be policy/configuration, not hidden magic.

Pattern: GOAP action selection

GOAP produces candidate plans from preconditions and effects. A structured scoring layer can rank plans or actions without asking an LLM to improvise the entire control loop.

goal: "package is release-ready"

world state
  tests = failing
  changeset = missing
  pack = unknown

actions → run_tests · add_changeset · npm_pack · verify_install · release

planner → valid plans → utility/confidence scoring → next action

Pattern: Retrieval routing

Do not query every memory and index on every turn. Decide which corpus is appropriate first.

QuestionLikely corpus
“Where is this symbol defined?”AST/code graph
“What did we decide last week?”memory/work history
“What is the package contract?”repository/docs
“What does Cloudflare currently support?”fresh web/provider docs

Pattern: Terminal lane selection

AgentSam has local, remote, and sandbox lanes. The agent should select the lane from task requirements and machine state instead of using a single hardcoded terminal.

lane decision
{
  task: "run repository tests",
  requiresLocalFiles: true,
  untrustedCode: false,
  available: { local: true, remote: true, sandbox: true },
  choice: "local"
}

Pattern: Approval gates

Agent autonomy should increase with reversibility and confidence. It should decrease as risk, blast radius, or uncertainty rise.

low risk + reversible + high confidence → act
medium confidence / missing evidence → inspect / test / verify
high consequence / irreversible → explicit approval

AgentSam application: skill selection

Skills are a perfect finite-choice problem. Retrieval produces a candidate set from the skill registry; the decision layer selects or ranks candidates using task type, route keys, tags, publication state, previous success, and confidence.

user intent → skill retrieval → rank / choose → invoke selected skill

AgentSam application: model routing

Model selection should remain user-visible and fail closed, but a decision layer can recommend a class based on context size, reasoning need, latency target, provider availability, and cost.

Task shapeSuggested class
Small edit, extraction, classificationfast
Normal coding and planningstandard
Large architectural reasoningreasoning/heavy
Private/local or offline worklocal model when capable

AgentSam application: package and deploy gates

Release readiness can be a machine-readable state rather than an LLM opinion.

release state
{
  manifestValid: true,
  testsPassing: true,
  packDryRun: "pass",
  standaloneImport: "pass",
  risk: 0.11,
  gate: "ready_for_review"
}

Design rules

  • Use typed decisions only when the output space is genuinely constrained.
  • Keep state explicit. Do not hide critical facts in giant prompts.
  • Never turn confidence into permission by itself. Permission comes from policy.
  • Prefer deterministic checks over learned judgment when a direct check exists.
  • Use the LLM when the task is generative or explanatory.
  • Record decisions as receipts. Candidate set, chosen result, scores, policy, and evidence should be inspectable.
  • Escalate uncertainty. Low confidence should trigger evidence gathering, a stronger model, or the user.
  • Keep presentation separate from control. CLI, Studio, and mobile can show the same underlying decision differently.
The intended AgentSam shape: an LLM-supercharged coding environment on top of Systematic Autonomous Machinery that understands state, tools, capabilities, costs, constraints, goals, and confidence.
