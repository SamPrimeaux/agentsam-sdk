# Product Requirements Documents

Use PRDs for user problems, product promises, product boundaries, lifecycle, required capabilities, acceptance cases, and definition-of-v1 criteria.

## Convention

- File names: `PRD-product-name.md`
- Product status should be explicit: `Experimental`, `Alpha`, `Beta`, `v1`, or `Deprecated`.
- PRDs may evolve as product requirements become clearer.
- Keep architectural authority decisions in ADRs and link to them rather than duplicating decision history.
- Requirements should distinguish current public surface, near-term work, and later capabilities.
- Acceptance criteria should include direct, indirect, sparse-context, rich-context, authorization, error, and out-of-scope behavior where relevant.

## Current PRDs

PRDs describe **what the product must accomplish**. ADRs describe **why architecture and authority boundaries are fixed a certain way**.
